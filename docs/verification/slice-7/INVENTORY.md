# Schreibwege · Bestandsaufnahme und Zielzustand

Priorität 1: `rates` INSERT/UPDATE/DELETE war unter eigener RLS direkt erlaubt: keine RPC-Snapshotprüfung, keine Korrekturfassung. `contracts` direkt beschreibbar: Abrechnungs-/Konfliktprüfung umgehbar. Fortführungsbeleg hatte ON DELETE CASCADE zum Ergebniszeitraum: nach dessen Löschung konnte derselbe Schlüssel wieder ausführbar werden. Breite Standardrechte enthielten sogar TRUNCATE (RLS schützt das nicht). Priorität 2: Konditions-RPC sperrte Zeitraum vor Zähler, andere RPCs umgekehrt. Keine deklarative Konditionseindeutigkeit. Belege ohne Zeitinformationen und mit vollständigen Snapshots. Direkte Ablesungen ohne serverseitige Werte-/Zukunftsprüfung und ohne Wiederholbeleg bei verlorener Insert-Antwort; beliebige Meterfelder direkt änderbar.

## Verbraucher und endgültig erlaubte Wege

| Aufgabe / Client | Tabellen / RPC | Zugriff und Regeln / Sperren |
|---|---|---|
| `contract-form.tsx` Einrichtung | `setup_meter` → meters, contracts, rates, readings, meter_setup_requests | auth.uid, Requestlock (Konto+UUID, Namespace 0), eine Transaktion; Typ/Name/Datum/Preise/Gasfaktor/Anfangsstand; neue Objekte |
| `reading-dialog.tsx` Stand | `record_reading` → readings, reading_requests; DELETE in contract-detail | auth.uid, Requestlock Namespace 7 → eigener Meter → atomarer Insert/Minimalbeleg. RLS über eigenen Meter für SELECT/DELETE; kein direkter Client-INSERT/UPDATE. Trigger prüft endliche, nichtnegative Werte und Datum ≤ Berlin-heute. Keine Monotonie-/Dezimal-/Zeitraumregel; neue bewusste Schlüssel dürfen gleiche Ablesungen erzeugen |
| `history-lists.tsx` Konditionen | `change_conditions` → rates, condition_revisions, condition_requests | auth.uid, Requestlock Namespace 4 → Meter → Zeitraum → Zeitraum-Advisory 4 → Rates nach ID. Erwartete Historie/Zeitraum, neue Datumsgrenzen, Werte/Faktor, explizite Korrektur/Löschung mit vorheriger Fassung. Replay liefert aktuelle Historie |
| Fassungsarchiv lesen | condition_revisions SELECT | RLS prüft eigenes Konto UND derzeit eigenen Zeitraum; keine Clientmutationen |
| `PeriodEndDialog.tsx` | `set_billing_period_end` → contracts | auth.uid, Meter → Zeitraum; erwartete Grenzen, absolute identische Wiederholung, exklusive Endgrenze, Nachfolger/Überlappung; kein Beleg nötig |
| `BillingSettlement.tsx` | `save_billing_settlement` → contracts | auth.uid, Meter → Zeitraum; Periodensnapshot, erwarteter Betrag/Datum oder bereits gleicher Zielwert; bekanntes Ende, endlicher Betrag/Datum; explizite Null |
| `BillingContinuation.tsx` | `continue_billing_period` → contracts, rates, billing_continuation_requests | auth.uid, Requestlock Namespace 5 → Meter → Zeiträume nach ID → Advisory 4 → Rates nach ID. Erwartete Zeiträume/Rates, neuester Zeitraum, Grenzen/Bestätigungen/übernommene Konditionen; atomare alte Grenze, neuer Zeitraum, Konditionen, Beleg |
| Beginn/Anbieter in `contract-detail.tsx` | neu `save_billing_period_details` → contracts | ersetzt den letzten legitimen direkten Zeitraum-UPDATE; auth.uid, Meter → Zeitraum; erwartete Start/Ende/Anbieter oder gleicher Zielwert; endlicher Beginn, Überlappungstrigger, keine neu ausgeschlossenen Konditionen/Abrechnung |
| `meter-management.ts` Name | meters UPDATE(name) | RLS eigenes Konto, Trigger trimmt / mindestens 2 Zeichen, bestätigte Serverzeile; absolute Wiederholung |
| Zähler löschen | meters DELETE | RLS eigenes Konto; Meterzeilenlock, FK-Kaskaden; bestätigtes Fehlen nach separat geprüfter Sitzung. Keine direkte Zeitraum-/Rate-Löschung mehr |

Rates/Contracts nur SELECT für authenticated; sämtliche Mutationen durch begrenzte SECURITY DEFINER-RPCs. Meters nur SELECT/UPDATE(name)/DELETE; Readings nur SELECT/DELETE; INSERT ausschließlich über Einrichtungs-/Ablesungs-RPC. Anon und PUBLIC ohne Tabellenrechte; keine Clientrechte TRUNCATE/REFERENCES/TRIGGER. Existierende eigene RLS bleibt als zusätzliche Grenze bestehen, auch bei den schmalen direkten Wegen. Private Belege RLS ohne Policies und ohne Clientrechte. RPCs authentifiziert, keine PUBLIC-/anon-Ausführung, search_path leer und Tabellen/Authfunktionen schemaqualifiziert. Triggerfunktionen nicht direkt clientausführbar. Vertrauensgrenze: postgres/service_role sind Verwaltungsrollen und können Regeln ändern; keine produktiven Clientschlüssel.

Gemeinsamer Meterlock serialisiert unterschiedliche Zeitraum-RPCs und Löschung, damit Snapshots nach Warten erneut gelesen werden. Rates-Parent- und Datums-Trigger bleiben erhalten; deklarative Unique-Constraint ergänzt sie. Historische Backups bleiben unabhängig: `contracts_backup`, `readings_backup`, `contract_prices_backup`, `contract_payments_backup`; Slice-6-RLS/Rechteentzug unverändert, keine Inhalte gelesen/bereinigt. `meters.user_id` hat NO ACTION zur auth.users: direkte Kontolöschung mit vorhandenen Zählern scheitert weiter, keine neue Löschfunktion.
